역할: 데이터 형식 변환·암호화·압축. 서로 다른 형식의 데이터를 통일된 형식으로 변환
PDU: 데이터 (Data) | 장비: 전용 장비 없음 (소프트웨어 처리)
기술/프로토콜역할특징
SSL / TLS암호화HTTPS의 기반. 대칭키+비대칭키 혼합 사용

MPEG / AVI동영상 압축동영상 데이터 형식 표준

5계층 — 세션 계층 (Session Layer)

역할: 응용 프로그램 간 논리적 연결(세션)의 시작·유지·동기화·종료 관리
PDU: 데이터 (Data) | 장비: 전용 장비 없음 (소프트웨어 처리)
프로토콜역할
NetBIOS윈도우 네트워크에서 세션 관리
RPCRemote Procedure Call. 원격 함수 호출
SSH (세션 관리 부분)원격 세션 유지
TLS 핸드셰이크암호화 세션 수립 과정

세션 vs 연결 차이

TCP 연결(4계층): 물리적 통신 경로
세션(5계층): 논리적 대화 단위
하나의 세션 = 여러 TCP 연결 가능

동기화 포인트

긴 데이터 전송 중 중간 저장점
오류 시 처음부터가 아닌
동기화 포인트부터 재전송

⚙️ 처리 방법 — 이 계층이 하는 일
기능내용

동기점 삽입

구분내용

⚠ 4계층 연결과 5계층 세션은 다르다
• TCP 연결(4계층) = 두 지점 사이의 물리적·논리적 통신 경로
• 세션(5계층) = 사용자 관점의 대화 단위

🤝 연결 설정과 해제

3-way 핸드셰이크 (연결)

① A → B : SYN
② B → A : SYN + ACK
③ A → B : ACK
→ 연결 수립 (ESTABLISHED)

4-way 핸드셰이크 (해제)

① A → B : FIN
② B → A : ACK
③ B → A : FIN
④ A → B : ACK → TIME_WAIT

해제가 4단계인 이유 — 한쪽이 FIN을 보내도 반대 방향은 아직 보낼 데이터가 남아 있을 수 있어서, 각 방향을 따로 닫는다(Half-close).
🚦 혼잡 제어 4단계 — 출제 1순위

실제 전송량 = min(cwnd, rwnd) — 혼잡 윈도우(네트워크 사정)와 수신 윈도우(상대 버퍼) 중 작은 쪽을 따른다. 흐름 제어는 rwnd, 혼잡 제어는 cwnd를 조절하는 것이다.

단계동작증가 방식
① 느린 시작
Slow Start		 cwnd = 1 MSS로 시작, ACK 하나마다 cwnd를 1씩 증가 → RTT마다 2배
임계값(ssthresh)에 도달하면 ②로 전환		 지수적
1 → 2 → 4 → 8
② 혼잡 회피
Congestion Avoidance		 ssthresh 이후에는 조심스럽게 RTT마다 1 MSS씩만 증가 선형
8 → 9 → 10
③ 빠른 재전송
Fast Retransmit		 중복 ACK 3개를 받으면 재전송 타이머 만료를 기다리지 않고 즉시 재전송 —
④ 빠른 회복
Fast Recovery		 재전송 후 cwnd를 1로 떨어뜨리지 않고 ssthresh부터 혼잡 회피로 복귀 (TCP Reno) 선형 재개
⚠ 손실을 감지하는 두 경로가 다르게 처리된다
· 타임아웃 (심각한 혼잡으로 판단) → ssthresh = cwnd2, cwnd = 1 → 느린 시작부터 다시 TCP Tahoe
· 중복 ACK 3개 (경미한 손실로 판단) → ssthresh = cwnd2, cwnd = ssthresh → 혼잡 회피로 복귀 TCP Reno
이 증감 방식을 AIMD(Additive Increase / Multiplicative Decrease)라 한다 — 늘릴 땐 더하기, 줄일 땐 반으로.
🔄 TCP 상태 전이 · TIME_WAIT
서버 : CLOSED → LISTEN → SYN_RECEIVED → ESTABLISHED → CLOSE_WAIT → LAST_ACK → CLOSED 클라 : CLOSED → SYN_SENT → ESTABLISHED → FIN_WAIT_1 → FIN_WAIT_2 → TIME_WAIT → CLOSED
상태의미
LISTEN서버가 SYN을 기다리는 대기 상태
ESTABLISHED연결 수립 완료. 실제 데이터 송수신 중
CLOSE_WAIT상대 FIN을 받고 ACK를 보낸 상태. 내 쪽 close() 호출을 기다리는 중
TIME_WAIT마지막 ACK를 보낸 뒤 2MSL 동안 대기 (능동적으로 먼저 닫은 쪽만 거침)
📖 TIME_WAIT가 2MSL인 이유 두 가지 — MSL(Maximum Segment Lifetime) = 패킷이 網에 살아있을 수 있는 최대 시간
① 마지막 ACK가 유실되면 상대가 FIN을 재전송하는데, 이때 응답할 수 있어야 한다
② 이전 연결의 지연된 패킷이 같은 포트로 열린 새 연결에 섞여 들어가는 것을 막는다
⚠ 실무 · 기출 포인트
· TIME_WAIT 누적 → 먼저 연결을 끊는 쪽(주로 클라이언트·프록시)에서 발생. 포트 고갈의 원인
· CLOSE_WAIT 누적 → 애플리케이션이 close()를 호출하지 않은 것. 코드 버그의 신호

📨 ICMP / IGMP — 3계층 보조 프로토콜
3계층에는 IP 혼자 있는 게 아니다. IP는 배달만 할 뿐 실패를 알리지도, 그룹을 관리하지도 못해서, 그 빈자리를 ICMP(오류 보고) 와 IGMP(그룹 관리) 가 채운다.
프로토콜프로토콜 번호맡은 일
IP—주소 지정과 경로 배달 (비신뢰·비연결)
ICMP1배달이 실패한 이유를 알림 · 상태 진단 (ping · traceroute)
IGMP2멀티캐스트 그룹 가입·탈퇴 관리
ARP / RARP—IP ↔ MAC 주소 변환 (위 참고)
🧠 프로토콜 번호 4개는 그냥 외운다 — 「1 · 2 · 6 · 17」
ICMP 1 · IGMP 2 · TCP 6 · UDP 17. IP 헤더의 Protocol 필드에 들어가는 값이다.
ICMP·IGMP는 IP 안에 실려 전달되지만 상위 계층이 아니라 3계층에 속하는 동반 프로토콜이다. 시험 단골

⚠️ ICMP의 성격 — 자주 나오는 진술
• 오류를 알릴 뿐 고치지는 않는다. 복구는 상위 계층(TCP)이나 응용의 몫
• ICMP 오류 메시지에 대해서는 다시 ICMP를 보내지 않는다 (무한 반복 방지)
• 멀티캐스트·브로드캐스트 주소에 대해서는 오류 메시지를 보내지 않는다
• 단편화된 패킷은 첫 번째 조각에 대해서만 보낸다
• 보안: Smurf(브로드캐스트 ICMP 증폭) · Ping of Death(규격 초과 ICMP) 공격에 악용되어 방화벽에서 막는 경우가 많다
📡 IGMP — Internet Group Management Protocol
호스트가 라우터에게 "나 이 멀티캐스트 그룹 들을게요 / 안 들을게요"를 알리는 프로토콜. 멀티캐스트 주소는 D 클래스(224.0.0.0 ~ 239.255.255.255) 를 쓴다.
라우터 ──── Query (그룹 듣는 사람 있나요?) ────▶ 호스트들 라우터 ◀─── Report (네, 저 224.1.1.1 들어요) ──── 호스트 라우터 ◀─── Leave (저 이제 안 들어요) ──── 호스트 ← v2부터 ⇒ 아무도 Report 하지 않는 그룹의 트래픽은 그 구간으로 보내지 않는다

🏷️ VLAN — 가상 랜

물리적으로 같은 스위치에 꽂혀 있어도, 논리적으로 서로 다른 브로드캐스트 도메인으로 나누는 기술. 스위치 한 대를 여러 대처럼 쓰는 셈이다.

항목내용
분류 방식포트 기반(가장 일반적) · MAC 주소 기반 · 프로토콜 기반 · 서브넷 기반
표준 태깅IEEE 802.1Q — 이더넷 프레임에 4바이트 태그 삽입. VLAN ID는 12비트 → 4096개(사용 가능 4094)
트렁크 포트여러 VLAN 트래픽을 태그를 달아 한 회선으로 전달 (스위치 간 연결)
액세스 포트단말이 붙는 포트. 하나의 VLAN에만 속하고 태그 없음
VLAN 간 통신반드시 3계층 장비 필요 — 라우터(Router-on-a-stick) 또는 L3 스위치
장점브로드캐스트 도메인 축소 · 보안(부서 격리) · 물리적 위치와 무관한 그룹 구성 · 이동 시 재배선 불필요
⚠ 기출 — "VLAN이 다르면 같은 스위치라도 직접 통신할 수 없다". 통신하려면 라우터나 L3 스위치를 거쳐야 한다. 또한 VLAN은 스위치가 브로드캐스트 도메인을 나눌 수 있게 해주는 유일한 방법이다.

🧠 부호화 법칙 — 「A는 유럽, μ는 미국」
　A-law (A = 87.6) → E1 · 유럽 · 압축 특성 13절선

μ는 255, A는 87.6 — 숫자가 그대로 보기로 나온다. 절선 수는 13(A) · 15(μ) 로, 알파벳 순서 A → μ 가 13 → 15 로 커진다고 묶어 외운다.
⚠️ 가장 많이 틀리는 곳 — T1의 「채널당 56 kbps」
T1도 물리적으로는 64 kbps 슬롯이다. 그런데 신호(시그널링)를 위해 각 채널의 8번째 비트를 6프레임마다 빌려 쓰기(로버드 비트) 때문에, 실제 데이터로 쓸 수 있는 것은 7비트 × 8k = 56 kbps 가 된다.
E1은 16번 슬롯을 통째로 신호용으로 따로 떼어 놓아서, 데이터 채널은 온전히 64 kbps 를 쓴다.

🔑 원리 — 맨 앞 비트가 클래스를 결정한다
첫 번째 옥텟(8비트)의 앞부분만 보면 끝 0xxxxxxx → A 클래스 0 ~ 127 10xxxxxx → B 클래스 128 ~ 191 110xxxxx → C 클래스 192 ~ 223 1110xxxx → D 클래스 224 ~ 239 (멀티캐스트) 1111xxxx → E 클래스 240 ~ 255 (예약)
💡 왜 이 숫자들인가 — 앞 비트가 고정되면 남은 자리로 만들 수 있는 범위가 정해진다. 128 = 2⁷, 192 = 128+64, 224 = 192+32, 240 = 224+16. 경계가 128 → 192 → 224 → 240 으로 간격이 절반씩 줄어드는 것만 기억하면 범위표를 외울 필요가 없다.

문제 — 주소 낭비

호스트가 300대 필요한 회사는?
• C 클래스(254개) → 부족
• B 클래스(65,534개) → 65,234개 낭비

클래스 단위로만 나누면 딱 맞는 크기가 없다.

해결 — 경계를 자유롭게

서브넷팅 : 큰 네트워크를 잘게 쪼갬
CIDR : /8 /16 /24 대신 /26 /27 처럼 임의 지정
VLSM : 서브넷마다 다른 크기 사용
NAT : 사설 IP로 공인 IP 절약

→ 300대면 /23(510개)으로 딱 맞춘다.

📎 클래스는 기본 경계를 정하는 것이고, CIDR은 그 경계를 옮기는 것이다. 아래에서 그 경계를 옮기는 계산을 이어서 본다.
🧠 헷갈리는 지점 — 「1~126」과 「마스크 비트」는 무엇이 다른가
둘은 보는 대상 자체가 다르다. 하나는 IP 주소를 보고, 하나는 마스크를 본다. 같은 것을 두 번 구하는 게 아니다.
1~126 (클래스 판별)서브넷마스크 비트 구하기
무엇을 보나IP 주소의 첫 옥텟서브넷마스크 값 (IP는 안 본다)
답하는 질문"이 주소는 어느 집안 태생인가""실제로 어디서 자르는가"
누가 정하나주소 체계가 태생적으로 정해둠관리자가 설계해서 부여
결과물A/B/C/D/E + 기본 마스크 (/8·/16·/24)실제 네트워크 / 호스트 경계
🧠 한 문장 — 「클래스는 주소가 들려주는 이야기, 마스크는 관리자가 그어놓은 선」
둘은 따로 주어지고, 서로 달라도 정상이다. 오히려 다르기 때문에 서브넷팅이 성립한다.
❓ 왜 하필 1~126인가
A 클래스는 선두 비트가 0 → 원래 범위는 0 ~ 127 0.x.x.x → "이 네트워크 자신"을 뜻하는 예약 ✗ 127.x.x.x → 루프백 (127.0.0.1) ✗ ───────────────────────────────────────────── 1 ~ 126 → 실제로 쓰는 범위 ✓
여기서 얻는 정보는 딱 하나 — 기본(default) 마스크가 /8 이라는 것. 즉 "원래대로라면 앞 8비트가 네트워크" 라는 출발점일 뿐이다.
📏 마스크 비트는 그 출발점을 「오른쪽으로 민」 결과
빌린 비트 = 실제 마스크 비트 − 클래스 기본 비트 서브넷 수 = 2 ^ (빌린 비트) 호스트 비트 = 32 − 실제 마스크 비트 유효 호스트 = 2 ^ (호스트 비트) − 2
📖 기출로 확인 — 둘이 반드시 함께 필요한 경우
Q. 클래스 B 주소에 서브넷 마스크 255.255.255.240을 적용하면 서브넷 수와 호스트 수는?
단계어디서 나온 값인가계산
클래스 B → 기본 /16클래스 판별에서첫 옥텟 128~191
240 = 11110000 → /28마스크에서1의 개수 8+8+8+4
빌린 비트 12두 값의 차이28 − 16 = 12
서브넷 4,096개빌린 비트에서2¹² = 4,096
호스트 14개마스크에서만32−28=4 → 2⁴−2 = 14
⚠️ 여기서 클래스가 왜 필요한가
마스크만 보면 /28이라는 사실만 알 뿐, 그게 몇 칸을 민 것인지 알 수 없다. 출발점(/16)을 알려주는 것이 클래스다. 반대로 클래스만 알면 실제 경계를 모른다. 서브넷 개수 문제에서만 둘이 반드시 함께 필요하다.
🧠 헷갈릴 때 딱 하나만 — 「호스트냐 서브넷이냐」
• 호스트 수만 물으면 → 마스크만 보면 끝 (클래스 몰라도 된다)
• 서브넷 수를 물으면 → 클래스 + 마스크 둘 다 필요

예제 — IP 192.156.100.68 / 마스크 255.255.255.224 의 네트워크 주소?

앞 3옥텟은 마스크가 255 → 192.156.100 그대로
마지막 옥텟만 AND 연산:

  68  = 0100 0100  (IP) 224  = 1110 0000  (마스크) AND ─────────────────────   64  = 0100 0000  (네트워크)

→ 네트워크 주소 = 192.156.100.64

⚡ 더 빠른 방법 — 블록 크기로 구간 찾기

① 블록 크기 = 256 - 224 = 32
② 서브넷 경계 (32씩 증가):
  0 · 32 · 64 · 96 · 128 · 160 · 192 · 224
③ 68은 64 ~ 95 구간에 속함

→ 네트워크 주소 = 192.156.100.64

🔀 HDLC vs LLC — 헷갈리는 이유와 차이
한 줄 정리 — LLC는 HDLC에서 갈라져 나온 자식이다. 그래서 프레임 종류(I/S/U)와 순서번호 방식이 똑같아 보이지만, HDLC는 데이터링크 계층 전체를 혼자 담당하고 LLC는 데이터링크의 상위 절반만 담당한다.

⚠ 함정 문제 3종
· "LLC의 주소 필드는 목적지 주소인가?" → 아니다. DSAP/SSAP는 상위 프로토콜 식별자(SAP)이지 노드 주소가 아니다. 노드 주소 = MAC 주소.
· "LLC도 흐름·오류 제어를 하는가?" → Type 2에서는 한다. 다만 실제 이더넷은 대부분 Type 1(비확인 비접속, UI 프레임)만 쓰고 신뢰성은 TCP에 맡긴다.
· "HDLC는 LAN 프로토콜인가?" → 아니다. HDLC는 WAN 점대점용. LAN의 2계층은 LLC + MAC.
📖 한 문장 암기 — HDLC는 WAN에서 혼자 다 하고, LLC는 LAN에서 MAC과 나눠 한다. 플래그·비트스터핑·FCS가 있으면 HDLC, DSAP/SSAP가 보이면 LLC.
